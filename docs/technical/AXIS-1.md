# Axis 1: The Hardware-Synchronized Temporal Core Engine

Axis 1 governs how the Holy Rust Unikernel OS (HR-OS) models time, handles hardware interruptions, and transitions between discrete computation states. Because HR-OS executes entirely within Ring 0 / EL1, the scheduler operates without virtual memory translations, page-table swaps, or privilege boundary traversals.

---

## 1. Formal Mathematical Model of the Task System

### A. System State Space Definition

Let the CPU state space `S` at any discrete time `t` be defined as the tuple of physical processor registers:

```text
S = (R, SP, PC, FLAGS)
```

Where:

- `R = {R0, R1, R2, …, Rk}` represents the set of general-purpose architectural registers (`k=15` for x86_64/ARM32, `k=30` for ARM64/RISC-V).
- `SP ∈ ℕ_32/64` is the physical Stack Pointer register.
- `PC ∈ ℕ_32/64` is the Program Counter (Instruction Pointer).
- `FLAGS` is the hardware status register (e.g., `xPSR`, `RFLAGS`, or `PSTATE`).

### B. Task Control Vector (T)

A task `Ti` within HR-OS is a finite state machine bounded by its allocated stack memory frame and execution context:

```text
Ti = (SP_limit, SP_base, SP_current, PC, State)
```

Where:

- `[SP_limit, SP_base]` defines the bounded linear memory range in SRAM/DRAM for task `i`'s isolated stack frame.

### C. Discrete State Transition Function

Let `T = {T0, T1, …, TN-1}` be the set of active tasks managed by a deterministic circular queue or priority ring. The scheduling function `σ: T → T` selects the next task upon a hardware timer tick event:

```text
σ(Ti) = T(i+1) mod N
```

The context switch is a bijection `Φ: S × T_old × T_new → S'` that updates the physical CPU registers.

## 2. Hardware Timer & Interrupt Mechanics

The scheduler is driven by a periodic physical clock interrupt generated by an on-chip hardware timer (ARM SysTick, APIC Timer, or RISC-V `mtime`).

### A. Timer Hardware Mathematical Configuration

To generate a deterministic context-switch interval `Δt` (e.g., `1 ms = 10⁻³ s`) given a system CPU clock frequency `f_CPU`:

```text
N = f_CPU × Δt
```

**Concrete Example (84 MHz Processor, 1 ms Quantum):**

```text
N = 84,000,000 × 0.001 = 84,000 cycles
```

### B. Hardware MMIO Configuration Registers

The timer is driven directly via volatile memory-mapped register writes:

1. Write Reload Value `N` to Timer Reload Register (e.g., `STK_LOAD` at `0xE000E014`)
2. Clear Current Counter Value Register (e.g., `STK_VAL` at `0xE000E018`)
3. Enable Timer, Enable Clock Source, Enable Vector Interrupt (`STK_CTRL` at `0xE000E010`)
   - Control Bitmask = `(ENABLE | TICKINT | CLKSOURCE) = 0x00000007`

## 3. Physical Memory Layout of the Execution Stack Frame

When a hardware timer interrupt fires, the CPU hardware performs an automatic exception stacking sequence before executing the first line of kernel assembly code, saving volatile registers directly onto the current task stack.

### Stack Layout During Context Switch

```text
  Higher Memory Addresses (Stack Top)
  ┌─────────────────────────────────────────┐  ◄── SP Base (Initial Entry)
  │ xPSR / RFLAGS   (Status Register)      │  ▲
  │ PC / RIP        (Return Address)       │  │ Automatically pushed
  │ LR / Link Reg   (Return Link)          │  │ by Hardware CPU on Interrupt
  │ R12             (Scratch Register)     │  │ (e.g., ARM Cortex-M / x86 Exception)
  │ R3              (Argument 4)           │  │
  │ R2              (Argument 3)           │  │
  │ R1              (Argument 2)           │  │
  │ R0              (Argument 1)           │  ▼
  ├─────────────────────────────────────────┤  ◄── Stack Pointer after Hardware Auto-Stack
  │ R11             (Callee-Saved)         │  ▲
  │ R10             (Callee-Saved)         │  │ Manually pushed
  │ R9              (Callee-Saved)         │  │ by HR-OS Kernel Scheduler
  │ R8              (Callee-Saved)         │  │ Assembly Instructions
  │ R7              (Callee-Saved)         │  │
  │ R6              (Callee-Saved)         │  │
  │ R5              (Callee-Saved)         │  │
  │ R4              (Callee-Saved)         │  ▼
  └─────────────────────────────────────────┘  ◄── New Top of Stack (T_old.SP)
  Lower Memory Addresses (Stack Limit)
```

## 4. Complete Execution Sequence & Context-Switch Phase Analysis

The complete, deterministic sequence of an HR-OS context switch occurs in 6 discrete phases:

```text
[Phase 1: Hardware Trigger] ──► [Phase 2: Auto Stacking] ──► [Phase 3: Manual Context Save]
                                                                     │
[Phase 6: Instruction Resume] ◄── [Phase 5: Context Restore] ◄── [Phase 4: Scheduler Update]
```

### Phase 1: Hardware Assertion & Pipeline Halt

- The hardware timer counter decrements to 0.
- The Interrupt Controller (NVIC / APIC / GIC) asserts the timer interrupt vector line.
- The CPU completes or aborts the currently executing micro-instruction in the pipeline.

### Phase 2: Hardware Auto-Stacking

- The CPU uses the active Stack Pointer (`SP`) to push the volatile register frame: `xPSR`, `PC`, `LR`, `R12`, `R3`, `R2`, `R1`, `R0`.
- `SP` is automatically decremented by the stack frame size (32 bytes for 32-bit CPU, 64/128 bytes for 64-bit CPU).
- The CPU fetches the interrupt handler address from the vector table in memory and loads it into `PC`.

### Phase 3: Kernel State Preservation (Manual Push)

- HR-OS kernel entry code executes in Ring 0.
- The remaining callee-saved registers (`R4` through `R11`) are pushed onto the current stack frame via a single multi-register push instruction.
- The final stack memory address is saved into the active task's control block:

```asm
TCB[T_old].SP = SP
```

### Phase 4: Deterministic Scheduler Execution

- HR-OS evaluates the circular task queue:

```text
T_new = T[(current_index + 1) % N]
```

- The global active task pointer is updated:

```text
current_task = T_new
```

- The physical Stack Pointer is updated to the incoming task's previously saved stack frame:

```asm
SP = TCB[T_new].SP
```

### Phase 5: Target State Restoration

- The kernel pops the callee-saved registers (`R4` through `R11`) from the new stack frame into CPU registers.
- `SP` increments accordingly.

### Phase 6: Hardware Unstacking & Execution Branch

- The kernel executes an exception return instruction (e.g., `BX LR` with `EXC_RETURN` payload, or `IRET`).
- The CPU hardware automatically restores `R0–R3`, `R12`, `LR`, `PC`, `xPSR` from the new stack frame.
- Execution instantly resumes at the new task's `T_new.PC` instruction within `EXEC_BUFFER`.

## 5. Latency & Cycle Cost Determinism Matrix

Because HR-OS operates strictly within Ring 0 without MMU virtual translation, the cycle cost of a context switch is 100% constant and deterministic:

| Phase     | Operation                         | Execution Cycle Cost (ARM Cortex-M4 / RISC-V Core) |
| --------- | --------------------------------- | -------------------------------------------------- |
| Phase 2   | Hardware Auto-Stacking            | 12 clock cycles                                    |
| Phase 3   | Manual Push (R4 - R11)            | 8 clock cycles                                     |
| Phase 4   | Circular Index Pointer Update     | 3 clock cycles                                     |
| Phase 5   | Manual Pop (R4 - R11)             | 8 clock cycles                                     |
| Phase 6   | Hardware Auto-Unstacking + Branch | 12 clock cycles                                    |
| **TOTAL** | **Full Context Switch Latency**   | **43 Clock Cycles (≈ 0.51 µs at 84 MHz)**          |

> Compare this to Linux/Android on ARM64, where context switches require 1,000 to 10,000 clock cycles (10–100 µs) due to MMU page-table swaps (`TTBR0_EL1`), privilege boundary traversals, and cache flushes.
